# Workspace minimum viable proposal

No live Workspace endpoints, invitation model, permission grants or persistence ports are created here. Existing workspace/membership tables and tenant SQL constraints remain unchanged. All registry operations are `proposed-not-implemented`; each waits for the named Workspace vertical-slice dependencies and human policy approval.

| Operation | Bound / response | Authority and future dependencies |
| --- | --- | --- |

Membership cursor binds actor/workspace/filter/order/policy revision; last tuple retained after deletion. A status/role/revocation change invalidates authorization revision before continuation; inaccessible membership gets404 before cursor facts. Administrative list may show invited/suspended rows as management data; those rows have no access themselves. Paging never means loading all users. Duplicate role/status filters and unknown query keys fail400.

## Creation and invitation transitions

Creation body remains name/slug only. A creator need not already have any membership. Unique slug conflict stays generic; same-key result cannot create a second workspace. Other existing users receive no grants. Initial administrator is returned only after confirmed atomic commit; uncertain commit503 uses same-key reconciliation. Existing last-admin and tenant invariants must pass real concurrent SQL tests before implementation approval.

Proposed invitation record (additive future design, not Prisma schema): server UUID, tenant, canonical credential email, allowed role, issuing membership and policy revision, keyed proof digest/key ID, primary issue/expiry (proposed24h), consumed/revoked timestamps, attempts and durable delivery outbox. Independent invitation token domain/key; no plaintext in DB/queue/log/URL. Email normalization must reuse credential rules rather than claim ownership of User.contactEmail. Durable retry/lease/exhaustion behavior requires separate review; verification/recovery outboxes are not silently repurposed. Delivery occurs after transaction commit and cannot itself grant authority.

Acceptance transaction derives target from verified proof, locks current user/family → workspace → ledger → credential/invitation → membership in a reviewed consistent order, validates current issuer invite grant, enabled recipient and verified exact credential, active workspace, primary expiry/unused state, then consumes proof and inserts membership/advances policy revision atomically. Concurrent redemption yields at most one effect; known rollback/invalid/expired/revoked/mismatch returns the same accepted envelope, while infrastructure unknown503 is not success. Existing ACTIVE membership is retained without elevation, INVITED may become ACTIVE only under approved acceptance policy, SUSPENDED cannot be unsuspended. No ADMIN role or extra team membership inferred. Last-admin safeguards remain untouched.

Generic acceptance is not evidence of joining: frontend refreshes existing workspace list/self APIs and uses server-confirmed membership. Invalid acceptance exposes no workspace/name/email/proof validity. There is no unauthenticated invitation preview contract here. Rate proposals for review: request5/hour per authenticated administrator +10/hour/workspace, acceptance10/15min/account +30/15min/trusted IP, durable proof attempts10; Valkey outage503, no refund/counter-reset assumptions. Numeric policy, invitation lifetime, recipient privacy, delivery/retention, role delegation and re-invitation semantics require approval and real tests.

Capabilities never authorize later actions. OBSERVER and archived workspace responses cannot advertise mutation capability; dependency write/completion booleans remain false until policy/DAG validation is approved. New actions require an explicit additive matrix/client contract update, not arbitrary strings or a generic @Roles bypass. [Authorization matrix](authorization.md) and [lifecycle rules](lifecycle.md) are mandatory companions.
