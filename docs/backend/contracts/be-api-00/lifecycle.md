# Proposed revisions, cursors and durable replay

Every infrastructure object in this document is **an implementation dependency**, not an existing table/key/port. Existing primary auth epochs/families and tenant locks remain authoritative; revision tokens never replace them. [Registry](registry.json) records machine-readable invariants and scenario examples validate a documentation decision model, not actual PostgreSQL/Valkey security.

## Revision ownership and invalidation

The owning database capability, not HTTP clients, owns monotonic positive BIGINT revisions, transported as decimal strings. Proposed records: workspace authorization revision (membership status/role, team membership, permission facts), workspace resource revision (creation/update/archive/delete), graph revision (edge, endpoint state/visibility/lifecycle changes), and layout snapshot revision bound to graph/filter/algorithm version. Proposed account workspace-list revision changes with any of its membership transitions. Existing User.authEpoch does not stand in for workspace policy revision.

Mutations advance affected revisions atomically with business changes. Membership/team changes also invalidate graph/filter snapshots and all affected actor projection caches. Resource changes invalidate list/overview/My Work/graph where relevant. Conservative workspace-wide invalidation first; narrower dependency tracking requires separate proof. DB revisions + current authority are checked before cached response/304. At-least-once invalidation delivery may lag; stale cache never overrides current primary revision. A reviewed durable business outbox is needed for distributed cache/event cleanup; current verification/recovery outboxes do not serve this purpose.

Live immutable `(createdAt,id)` paging does not reject every data revision change: deleted rows disappear, cursor tuple survives deletion, earlier/later inserts follow comparator and optional immutable first-page watermark, and updates may change filter inclusion. Rows can be skipped/revisited by changing filters, so dedupe and refresh; no snapshot/export guarantee. Authorization revision change causes409 CURSOR_STALE **after** current scope authorization; revocation/inaccessible scope gives404 first. Graph/layout/mutable-sort cursors require matching data+policy revisions; any change restarts. Changing query/fields/sort/actor/tenant/root gives400. No retained row ID needed to validate an immutable tuple.

## Cursor key lifecycle

Independent256-bit HMAC-SHA256 cursor key, domain label `unblok-api-cursor-v1`; never reuse session/email/recovery secrets. Signed canonical payload binds key ID/version, actor, operation, tenant/root, filter/projection/sort hash, tuple/watermark, revisions and exact issued/expiry times. No plaintext hidden-resource metadata. Registry example payloads are internal synthetic verification facts, **not browser authority or real bearer tokens**.

TTL≤900seconds for lists; graph handle TTL≤120seconds within that bound. Validate signature before trusted payload use, safe parsing/length bounds, issuance≤now<expiry and declared TTL. Rotate by deploying new active signer to all replicas; retain previous verify-only key until its last issued cursor TTL + bounded deployment/clock margin (proposed60seconds). Do not re-sign old payloads to extend expiry. Retired/unknown key denies400. Compromise removes the key immediately, purges associated traversal state and forces restart even before TTL. Key-unavailable503; no unsigned acceptance. Secrets provisioned by reviewed manager, IDs nonsecret, logs omit cursor/body; current namespace/key restoration runbook must invalidate restored traversal handles before reopening. No keyring implementation exists.

Fresh cookie/primary authorization precedes cursor-scope disclosure. Then verify bindings/revisions. Previously minted principals expire at callback/abort; next page uses new boundary. No instant revocation of already delivered data or cache-expiry cancellation claim.

## Idempotency persistence and concurrency

Proposed PostgreSQL ledger columns: UUID id; actor user UUID; nonnull scope key (`workspace:<uuid>` or `account:<actor>` for workspace creation); operation/version; UUID key;32-byte canonical payload digest; state; bounded HTTP result/status or immutable result references; created/completed/retention timestamps. Unique(actor,scope,operation,key); FK/tenant ownership and strict byte/result/check constraints reviewed in an **additive future migration**. Do not use nullable workspace uniqueness for account operations. Request bodies may contain email/proofs: ledger uses a domain-separated keyed digest, never persisted plaintext body/token. Result stores no secret/cookie/CSRF token and still requires current resource authorization on replay.

First durable transaction inserts reservation and locks it, then business effect + terminal result + data/policy revisions + necessary outbox records commit together. No acknowledged effect without committed terminal result; no standalone committed IN_PROGRESS reservation in the minimum design. Concurrent same-key contenders meet the unique-row lock: bounded wait, then matching committed result replay; different digest409; unresolved contention409+Retry-After. All transactions validate account/session/membership first and at completion. Ledger doesn't let a revoked actor replay data. Unknown commit returns503, never presumed canceled; subsequent same-key lookup on primary either finds terminal result or, after original transaction is known aborted/absent and unique-lock resolution, executes once. Do not create a new key while outcome is uncertain. Timeout does not prove lock holder rolled back.

Proposed minimum full-result retention24hours after completion; thereafter strip result/PII to a minimal keyed tombstone retaining actor/scope/operation/key/digest until an explicitly approved purge policy. Same key after full-result retention returns409 IDEMPOTENCY_RESULT_EXPIRED, never re-executes. No automated tombstone purge/reuse window is approved; retention/privacy/capacity and actor-deletion behavior remain human decisions. This intentionally supersedes the earlier ambiguous24h ledger deletion wording. Restoration requires effect/ledger consistency review before retries; no exactly-once external-delivery claim. Worker consumers still require durable dedupe.

## Isolation, locks and required runtime proof

Preserve SERIALIZABLE and current acquisition/callback/lock/statement limits. Global order user → family → workspace (when existing) → idempotency row → graph → sorted resources. Account-only creation skips nonexistent workspace lock, uses account fence and ledger, then allocates new workspace + initial ADMIN atomically. Unique-scope keys and slug conflicts must be handled without leaking another workspace. Invitation acceptance additionally locks invitation/credential binding after workspace/ledger before membership effect, with a reviewed consistent order across issuance/revocation. Existing rows cannot be unsuspended or elevated through redemption.

Membership administration must acquire conflicting workspace lock and atomically change policy revision. Earlier shared read or protected write may commit first; acknowledged revocation prevents subsequently ordered stale operations. Bounded long read can delay revocation until lock deadline:503/unconfirmed, not success. No external I/O while holding locks. Complete-operation retry only on confirmed serialization/deadlock rollback and revalidation; unknown outcomes reconcile same key. Graph completion/writes remain denied until authoritative rules exist.

Multi-user checks must not acquire another user fence after holding workspace/ledger locks. Invitation acceptance discovers immutable recipient/issuer selectors first, then a future reviewed port acquires every required user fence in sorted UUID order, family locks sorted next, before workspace and later locks; re-read all discovered facts under those locks. A changed selector causes rollback/restart, not a lock-order shortcut. Existing request principal represents only the authenticated recipient; issuer policy is current primary membership facts, never a forged second principal. Discovery itself grants no authority.

Required future real-DB tests: both revocation/read lock orders; same-key overlapping requests and different bodies; lost acknowledgement after commit; rollback before effect/result; logout/membership revocation before replay; expiry/tombstone behavior; key rotation/compromise and revision invalidation; concurrent insert/filter-update/delete cursor traversal; graph budget exhaustion and restored handle. Documentation scenario checks cannot substitute for these tests.
