## Persistence and narrow security boundary

Only the database package executes business SQL. New closed Tenancy capabilities own listing, issuance and acceptance, retaining the instance-owned unforgeable VerifiedPrincipal and request callback lifetime. No raw transaction, principal evidence, role decorator or generic database access is given to a feature service. The access guard adds only exact reviewed controller method references. Worker InvitationDelivery is composition-only; negative architecture fixtures reject direct/indirect feature use.

Additive migration `20261013000000_workspace_memberships_invitations` introduces Workspace policy revisions, scoped directory index and inviter composite binding, invitations, invitation outbox and minimal keyed idempotency receipts. Existing nine migrations are byte-preserved. Membership/Workspace lifecycle changes increment policy revisions; demotion/suspension of an issuer and Workspace archival cancel unconsumed proofs, preventing demote/re-promote or archive/unarchive resurrection. SQL enforces MEMBER/OBSERVER ceiling, exact inviter identity/user/tenant membership FKs,24-hour maximum, bounded attempts, immutable proof binding and irreversible consumption/cancellation/receipts. Existing last-admin/tenant constraints remain intact. Fresh replay and upgrade/schema parity are tested; no migration is applied to the operator's selected application database by the verification suites.

Proof is a cryptographic HMAC-SHA256 PRF over independent secret, random UUID challenge nonce, key ID, Workspace, inviter, epoch, canonical recipient email and role. A second independent domain stores only its keyed digest. This follows the existing durable derivation approach so a worker can reconstruct the same proof without plaintext DB/queue storage. Invitation, verification, recovery, session, cursor and receipt domains cannot be interchanged. API/worker must share the independent invitation key; key rotation invalidates pending old-key proofs rather than silently extending them. Issuance never looks up whether the recipient has an account; contact-email rows never bind proof or grant access. Redemption requires the current immutable password credential email and verified ownership. It does not link accounts or change verification state.

Issuance holds inviter account/family → Workspace UPDATE → immutable receipt → invitation/outbox, with no external I/O. Same current issuer/epoch/binding/email reuses retryable/delivered work and preserves its original role and deadline; first issuance determines that proof's role. Another issuer or retired key, expiry, exhausted proof or exhausted/unleased delivery cancels and replaces under the Workspace lock. An outstanding final lease is not assumed canceled; new requests wait for its bounded30-second lease to resolve/expire. Receipt commits with proof/outbox in the same SERIALIZABLE transaction; same-key same-body is inert replay, changed body conflicts. Receipts contain actor, operation, request key and keyed canonical body digest, not raw email/proof/result identity. Generic constant202 receipts need no secret/full-result cache, and never permit a second effect. No automatic purge/reuse is approved.

## Acceptance locks and concurrency

Before acquiring any user fence, a private primary selector reads the invitation's immutable issuer ID. All required user rows (recipient and issuer) are locked FOR SHARE in sorted UUID order. Recipient identity/family validation follows. A preliminary server-owned verified credential/email check rejects mismatched or unverified recipients before locking an unrelated Workspace; it grants nothing and eligible paths revalidate the credential later. Then Workspace UPDATE → receipt → recipient credential SHARE → invitation UPDATE → membership effect. The issuer gets no forged principal or session: current enabled state/epoch, immutable verified credential, same issuing membership and ACTIVE ADMIN role are read under these primary locks. Any missing/expired/stale recipient session fails before effect. Completion revalidates recipient epoch/family and the live request principal using already-held locks; no new user or Workspace authorization is acquired in reverse order. Selector/binding mutation is prohibited by SQL; SERIALIZABLE rejects races and missing snapshots rather than trusting discovery.

Correct proof requires current issuer epoch, active Workspace, enabled verified exact recipient, original identity/email binding, unused uncanceled unexpired proof and attempts<10. Only then consumption and membership activation commit together. Existing ACTIVE role remains untouched; SUSPENDED never activates; INVITED activation uses only the proof's MEMBER/OBSERVER ceiling. Incorrect matched-recipient proofs increment durable PostgreSQL attempts and return a value instead of throwing, so attempts commit despite generic202. Mismatched recipients cannot burn another account's proof budget. Concurrent losers return bounded409 on known serialization conflicts, and a fresh same-key request reconciles. Unknown commit503 does not mean cancellation; no automatic effect retry/new key.

[Actual concurrency observations](evidence/BE-WS-02-concurrency.json) record controlled primary lock waits, SQLSTATE40001, HTTP outcomes, lost acknowledgement and single membership effects. Tests hold/release real database transactions through test-owned proxies; production receives no hook or bypass. Earlier authorized operations can complete before revocation commits. Revocation-first denies the later operation or forces rollback/revalidation. Already delivered directory bytes cannot be recalled; no immediate revocation or cancellation claim is made.

### F1: acquisition versus validation

`lockAuthority` now owns one sorted/deduplicated user SHARE acquisition, including the immutable invitation issuer selector, followed by recipient family SHARE. It validates identity, enabled state, epoch, generation, SID digest, revocation and database-time expiry. Acceptance requires the recipient's one live family; issuer authorization uses its current user epoch, verified credential and original ACTIVE ADMIN membership, not an invented inviter live session.

Acceptance order: all required users in UUID order -> recipient family -> Workspace UPDATE -> receipt -> recipient credential SHARE -> invitation UPDATE -> membership effect. Discovery/prechecks are nonlocking and grant nothing. Completion calls internal `revalidateAuthority` with no new row locks, using existing user/family locks and a fresh database statement time. Shared Tenancy completion and rotation use the same held-lock validation rather than reacquiring earlier locks. Request-bound principal checks remain. No authority check is removed; the helper is internal to the database package and absent from its public entry point.

SID digests are not unique in SQL: `retireSid` previously interleaved user A/family A/user B/family B. It now discovers immutable bindings, acquires all users sorted first, then all families by UUID, conditionally retiring only still-matching digests. Single-family revoke remains user SHARE -> family UPDATE; rotate is user SHARE -> family UPDATE then nonlocking validation; logout-all is user UPDATE and epoch advancement. These paths do not acquire Workspace locks.

Membership mutation APIs remain absent. Lifecycle/maintenance transactions must prelock required users/families, then Workspace, any receipts/credentials and affected invitations in UUID order, then memberships. Historical triggers acquire Workspace/revision and cancel proofs during membership UPDATE: standalone raw UPDATE may acquire its target tuple before the BEFORE trigger, so it cannot be claimed to follow application order. Maintenance must prelock Workspace and affected invitations. Migrations are unchanged. Arbitrary DBA SQL can still deadlock; bounded rollback and fresh authorized reconciliation are required, never bypass or assumed cancellation.

Real PostgreSQL tests assign inviter/recipient from two generated accounts by sorted UUID, covering both orders. Acceptance is held at proof consumption while family revocation and correctly ordered inviter demotion overlap; observed family waits, actual serialization failures and fresh lifecycle reconciliation are recorded. Revocation-first tests hold the issuer epoch update and prove waiting acceptance grants nothing. A duplicate-SID test proves all users precede two sorted families and both are retired. Workspace lock traces assert exactly one user acquisition and one family acquisition, with no earlier lock acquired at completion. A deliberately inverted legacy raw membership update is also raced against acceptance to establish bounded deadlock/serialization handling and fresh inaccessible state, rather than assuming triggers alone impose lock order. Existing 1500ms lock,4000ms statement and test deadlines remain unchanged. A SERIALIZABLE rollback does not establish revocation success; failed lifecycle work is explicitly reconciled in a fresh transaction.

### F2: delivery eligibility is a lease-time snapshot

Eligibility is checked during lease acquisition and commit; locks do not span external I/O. An already-leased email may be sent after inviter demotion or Workspace archival. A late acknowledgement may mark delivery acknowledged, but cannot uncancel a proof or grant membership. Immediate external-email cancellation and exactly-once delivery are not guaranteed. Another pre-send read would still leave a race and cannot prove cancellation.

Two tests pause the send callback after the committed lease, verify the lease, commit demotion/archival and confirm the trigger canceled the proof, then resume actual existing-worker transport delivery into Mailpit. The received email contains the canceled proof. Real HTTP redemption returns generic202 with zero membership effects; canceled work cannot lease again. Redemption independently revalidates current issuer epoch/enabled state, verified credential, original ADMIN membership, Workspace and one-use/expiry/attempt state under primary transactional fences. Late mail cannot restore authority.
