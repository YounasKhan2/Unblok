## Implemented contracts

Complete generated schemas, paths, request headers and byte limits: `docs/backend/evidence/BE-01B-openapi.json`, generated by `scripts/backend/workspace-administration-contracts.ts`. These are additive routes in the existing Workspaces module and closed Tenancy capabilities, over the existing invitation ledger/outbox. Existing v1 issuance, acceptance, DTOs and generic acknowledgments remain compatible.

Prefix `A = /api/v1/workspaces/:workspaceId/administration`:

| Method/path | Behavior |
| --- | --- |
| GET A/memberships | Member ID/name/nullable contact email/Workspace role/status/joinedAt/removedAt/row revision; server-side status/role/literal search/Team filters; authoritative active/matching/pending totals. |
| GET A/memberships/:membershipId/teams | Bounded Team assignment continuation. The directory embeds five assignments plus an honest continuation cursor. |
| GET A/eligible-teams | Only active, nonquarantined Teams the caller actually owns with an explicit MEMBER ceiling. Workspace ADMIN alone is insufficient. |
| GET A/invitations | Paginated lifecycle history, exact matching total, requested Teams, delivery observations and revision. Optional lifecycle and literal email-search filters. |
| GET A/invitations/:invitationId | Scoped private administrator preview; no proof, digest, credential identity or session data. |
| POST A/invitations | `{email, role: ADMIN|MEMBER|OBSERVER, teamIds}`; at most 20 distinct canonical Team IDs, all validated. Neutral 202 `{status: "accepted"}`. |
| POST A/invitations/:invitationId/resend | Empty object, revision and durable key. Creates a new immutable generation, cancels predecessor and enqueues delivery atomically; does not promise mail delivery. |
| POST A/invitations/:invitationId/revoke | Empty object, revision and durable key. Cancels outstanding authority; cannot undo an accepted membership. |
| PATCH A/memberships/:membershipId | `{role}` with row revision/key; active memberships only; protects final active ADMIN and Team owners. |
| DELETE A/memberships/:membershipId | No request body; existing JSON content-type/Origin/CSRF requirements still apply. Soft removal retains membership identity/history, sets SUSPENDED and removedAt and invalidates access. |
| POST /api/v1/workspace-invitations/preview | Existing token-body vocabulary. Private detail only for verified matching credential owner possessing an authentic proof; other authenticated callers receive neutral `{status: "accepted"}`. No account-existence field. Own terminal lifecycle can be explained without permitting redemption. |

All new administration projections require an active, verified scoped Workspace ADMIN. Archived Workspace historical reads remain authorized; writes require active Workspace. Unauthorized/foreign scope is concealed with 404. Anonymous/stale sessions retain existing 401/CSRF behavior. No Workspace OWNER role is invented.

Every administration mutation requires a single UUID Idempotency-Key. Member edits/removal require If-Match containing the quoted member version (for example `"3"`). Invitation resend/revoke require the quoted opaque resource-specific revision returned on that invitation row (`"inv2-<invitation UUID>-<HMAC>"`); the Workspace-wide page revision is not a mutation validator. Reads return the appropriate revision in the body. Missing/stale preconditions produce 428/412; semantic/serialization conflicts are 409, stale cursors are CURSOR_STALE/409, rate denial is 429 with Retry-After, and unknown outcome/dependency failure is 503. Reauthorization precedes receipt replay. There are no automatic mutation retries.

Pages default to 20 and cap at 100; signed cursors bind actor/identity, Workspace, operation, normalized filters, page size, key ID, revisions and original 15-minute expiry. Invitation status is evaluated at the cursor's explicit snapshot time. Directory projection changes invalidate traversal. Cursor authority fingerprints also bind current scoped issuer epochs/disabled/verification state, without publishing those counts or introducing a Workspace revision write into logout-all.

Member pages are capped at 1 MiB, invitation pages at 2 MiB, Team pages at 64 KiB and individual previews at 32 KiB. These budgets accommodate bounded nested assignments and existing Unicode Team names. No directory page is treated as a total and no truncated assignment slice is represented as complete.

## Persistence and transaction details

One additive migration: `20261016000000_workspace_administration`. **13 total migrations** on disposable test databases; shared QA was not inspected or migrated. Original 12 migration files are unchanged.

- Membership removal timestamp/version and terminal removal guard retain references; there is no restore/readmission route. Existing suspended/removed identities cannot be activated by invitations.
- Versioned invitation metadata and immutable previous-generation linkage preserve all v1 rows/proof domains. Version 1 still cannot grant ADMIN. New proofs bind Workspace role, canonical Team assignment digest, issuer epoch and generation linkage.
- Normalized Team assignments have same-Workspace composite FKs, positive captured Team versions, at most 20 entries, immutable transaction-bound plan insertion and a deferred digest check. Captured versions prevent archive/restore or ownership/version changes from reviving an older assignment grant. Even metadata version changes invalidate the old Team grant. Invalidated or canceled generations cannot be resent; any new invitation must be an explicit new authorized issuance, not resurrection through resend.
- Existing immutable invitation receipts gain operation domains for administration; no raw proof is persisted in a receipt, queue or administration response. Existing indefinite receipt retention is preserved; no sweeper or audit deletion is introduced.
- Administration revision rows, projection triggers and scoped keyset/assignment indexes support bounded traversal. Authority epoch changes use a private read fingerprint rather than a new revision-row write, preserving revocation ordering.

Initial assignment acceptance reuses existing sorted user/family → Workspace serialization and final principal validation. Proof consumption, membership activation/creation, all Team joins and receipt commit together. Any invalid Team or changed captured Team version grants nothing. An injected failure during Team insertion rolls back all effects, after which an explicit same-key retry succeeds. Existing ACTIVE memberships are never elevated or assigned Teams through an invitation replay. Workspace administration cannot demote/remove a Team owner; the established consent transfer is required first. Independent security revocation is not blocked by Team ownership.

Resend rotates proof authority rather than mutating an issued proof. Acceptance/revocation serialize; consumed invitations cannot be retroactively revoked into removing access. A previously leased external email may still arrive after cancellation, but its proof cannot redeem. Lifecycle and delivery are distinct: PENDING/EXPIRED/REVOKED/ACCEPTED/SUPERSEDED/INVALIDATED versus QUEUED/DELIVERED/FAILED observations.

Repeated new issuance for an existing outstanding email is neutral and does not silently edit its role/Team plan or resend it; use explicit resend to rotate that generation. Administration writes conservatively share the existing invitation issuance budgets (5/actor/hour, 10/Workspace/hour, 30/IP/hour). Recipient preview shares acceptance admission. No rate/security budget was weakened.

Deploy only after review: apply the additive migration with the migration role, preserve backups/history and ensure the existing restricted runtime role has reviewed access to the new tables. No database reset/drop/force-resolve is part of application deployment. Large populated production migration locking/duration has not been certified. Do not mix old and new API instances once v2 issuance begins: old acceptance code does not apply initial Team assignments, and old workers cannot reconstruct v2 proofs. Drain old API/worker instances and deploy the matching API/worker code before v2 issuance; rolling mixed-version operation is not implemented or certified.

## Performance evidence and limits

`docs/backend/evidence/BE-01B-performance.json` records actual EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON), rows, buffers, timings, statement counts and response bytes. Populations contain 10k and 100k additional memberships and invitations, with real constraints/triggers enabled. Five sequential samples cover page sizes 1/100, member directory, literal member search and invitation history. Operation statement counts exclude exact bare `SELECT 1` Prisma pool-health pings, which are recorded separately alongside total wire statements; the observed difference was one pool-health ping, not an extra business lookup. The full closed Tenancy/session-fence path is measured; HTTP and Valkey network latency are excluded. Query events are synchronized by an observed measurement barrier, which is excluded from the operation's statement count.

Original implementation-head repeat (superseded by correction evidence for invitation validators) passed: 1 performance test / 0 failures / 178 assertions. Every operation/page size had 32 operation statements; health pings and total wire counts are present in the JSON. At 100k, median member-directory latency was 487.0 ms (limit 1) / 768.4 ms (limit 100), invitation history 147.8 / 151.9 ms, and literal member search 651.7 / 563.6 ms. The largest of the five samples was 1,684.1 ms. At 10k, medians ranged from 78.5 to 126.6 ms. Largest measured response was 30,324 bytes. These historical numbers describe the original implementation only; the refreshed artifact and current measurements are documented in BE-01B-SECURITY-CORRECTION.md. No SLO is inferred. These are local measurements, not a production SLO or concurrent administration-load certification. Dense Team assignments, large status-filtered invitation histories, broad Unicode search and production migration-lock costs need additional capacity testing. Nested Team projections are bulk/bounded; SQL statement count is checked against page size. Counts still scan matching index entries and are not claimed O(1).
