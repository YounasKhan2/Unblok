## Store and live authority

The dedicated node-redis connection disables offline queues, bounds connection startup and limits reconnect attempts. The Store wraps `get`, `set` and `destroy` with a 750ms callback deadline and generic unavailable errors. Callbacks settle once. Library command timeout remains defense in depth; it is not the security boundary. Store calls use connect-redis, not MemoryStore. No bulk session clear/scan API is exposed by the wrapper.

**Timeout is not cancellation.** A real isolated Valkey `CLIENT PAUSE 1200 ALL` test observes unavailable at the wrapper deadline, then the original SET persisting after the deadline; the callback remains failed. A blocked GET also returns unavailable. No client retry or late callback becomes authenticated success. Responses await explicit establishment/rotation saves. Failed saves suppress implicit express-session response-finalization save/retry and new SID delivery, clear the cookie, and attempt durable family revocation. Tests observe 503, expired clear-cookie, a real late payload and a revoked family. If the compensating PostgreSQL commit is unavailable/unknown, the orphan is **unconfirmed**, not proven revoked. No new SID is delivered by the failing operation, but privileged cache compromise/disclosure and orphan reconciliation require operational review; there is no joint PostgreSQL/Valkey transaction or cancellation claim.

`Sessions` owns private WeakMaps for actual middleware-processed Request objects and opaque verification assertions. Browser input, structural Request/principal objects, user IDs and authorization fields cannot create assertions. express-session verifies the signed cookie; the server requires a 43-character base64url SID generated from 32 random bytes. Duplicate (including whitespace-normalized names), oversized, malformed and forged cookie cases fail. The real verifier performs a **fresh bounded store lookup at each `withRequest` boundary**, separately from library hydration, validates strict Zod state/deadlines, derives SHA-256 from the actual presented SID, and returns minimal evidence to Tenancy. Tenancy validates identity/epoch/family/generation/digest against the primary before minting. No positive authority cache or identity fallback exists. A test deletes cache after middleware hydration while PostgreSQL authority remains valid and proves rejection. Multiple scoped queries produce only library hydration plus one verifier lookup, with no per-query Valkey calls.

The facade binds one Tenancy instance. It permits one authenticated callback per Request. The BE-00G registry/context lifetime remains; an optional server-owned AbortSignal now removes the principal on response finish/close or request abort. Callback completion/error removes it as before. A real HTTP disconnect followed by an inherited callback's scoped access is denied. Protected transactions retain PostgreSQL user→family→workspace→resource locks and entry/completion validation. No Valkey I/O is placed in those transactions. Earlier admitted requests may finish after cache deletion. Abort checks cannot cancel a commit already in progress, and revocation does not retract reads/responses/external work already released.

## Cookie, expiry and lifecycle

| Setting | Implemented infrastructure profile |
|---|---|
| Name | Production `__Host-unblok.sid`; loopback development `unblok.sid.dev` |
| Flags | HttpOnly, SameSite=Lax, Path=/, Domain omitted; Secure in production |
| Signing | Required independently generated 32–64 byte hex secret; up to three verification keys, current first; no default/test production secret |
| Idle deadline | 30 minutes; authoritative PostgreSQL deadline plus cache validation |
| Absolute deadline | 12 hours from establishment; immutable SQL family deadline |
| Anonymous CSRF state | 10-minute fixed lifetime, no identity/family/principal |
| Cookie maxAge / store TTL | Clamped to earliest idle/absolute deadline; TTL rounded up to seconds, application and primary checks still reject expired authority |
| Automatic renewal | `rolling:false`, `resave:false`, `saveUninitialized:false`; touch cannot extend TTL/deadlines; reads/polling do not renew |
| Qualifying renewal | Explicit server-owned rotation only; advances generation and SID digest atomically, fresh SID and CSRF; cannot extend absolute deadline |

Restored cookie bookkeeping cannot downgrade flags, Domain or Path: middleware reapplies the current profile. Expired/missing state clears the named cookie and denies. State stores only version, kind, identity/user/family references, epoch/generation strings, bounded deadlines and CSRF token; no roles, workspace/resource permissions, password or provider token. Extra grants/fields fail strict schema validation. Cache references alone never authorize. Cache-extended idle/absolute deadlines still fail the original PostgreSQL deadlines.

`establish` is server-private infrastructure for a **future** verified-credential application service; its injected resolver rejects all inputs in production. It regenerates SID/CSRF, creates a family through the approved DB capability and awaits a bounded save before success. A browser body cannot select an identity. `rotate` validates inside a fresh authenticated request, destroys the predecessor through regeneration, then advances the primary fence and saves the successor. Failure may log the user out; no availability rollback that revives predecessor authority is attempted. Simultaneous rotations are serialized by unchanged BE-00G fences. A delayed old Set-Cookie can cause re-login; it cannot restore old authority. Scheduled rotation, step-up credential policy and frontend retry behavior are still planned.

`logout` and `logout-all` are infrastructure methods, not endpoints. They require POST plus middleware origin/CSRF protection and fresh session authentication. Family revocation or epoch advancement commits **before** cache destruction/clear-cookie. Results distinguish confirmed durable revocation from confirmed/unconfirmed cache cleanup. An unconfirmed primary commit throws unavailable, never success inferred from cache deletion. All-session cache enumeration/notification is not implemented: other SIDs may remain until expiry but primary epoch validation rejects them. Underlying BE-00G family revocation is idempotent; transport retries may receive denial after revocation and need a future reviewed response contract. Late SET resurrection after logout/rotation/logout-all fails primary validation.

## Browser boundaries and ingress

Unsafe non-health requests require an exact configured Origin, valid constant-time synchronizer token and JSON content type. Missing, empty, `null`, suffix/multiple/disallowed Origin, missing/wrong token and simple form/text bodies are rejected. No Referer fallback, proxy-derived Origin, SameSite-only exemption or wildcard exists. Parsing/body limits and coarse shared-IP throttling run before session middleware in production. CORS adds X-CSRF-Token to explicit preflight headers; credentials are emitted only when `SESSION_CROSS_ORIGIN=true` and the exact origin is allowed. GET/HEAD/OPTIONS confer no principal; liveness skips session/TLS checks and remains dependency-independent. Readiness includes the dedicated store. Existing health responses and error normalization remain; unsafe unknown routes now encounter the CSRF boundary, not an authentication endpoint.

The infrastructure `bootstrap` method requires GET plus an explicit allowed Origin, sets no-store, and can intentionally persist bounded anonymous state. **There is no public bootstrap route.** A future handler must retain rate/body limits, no-store and exact-origin behavior; login and signup must retain token protection even before authenticated identity. Public-auth metadata/guard exemptions have not been added. No WebSocket handshake or message path exists: enabling one must separately validate exact Origin, signed cookie, fresh action-bound session/primary authority, authorized resource delivery, and revocation/disconnect behavior; never wrap a whole connection in one principal callback.

Development HTTP binds only loopback and rejects configured proxy trust. Production requires TLS-validated PostgreSQL/Valkey URLs via the existing config and rejects insecure non-health requests. Proxy trust defaults false; explicit IPv4 ingress addresses/CIDRs may be supplied, never blanket true, invalid addresses or /0. Direct API access must be blocked and trusted ingress must overwrite forwarded headers. The real certificate-verified HTTPS test proxies from trusted 127.0.0.2, emits __Host/Secure/HttpOnly/Lax/Path=/ without Domain, overwrites a spoofed forwarding header, and rejects direct/untrusted forwarded HTTPS and disabled trust. The API's current listener is HTTP: production HTTPS termination therefore requires the explicitly reviewed trusted ingress configuration. This loopback fixture is **not browser SameSite/CORS certification** or evidence of production certificate/ACL configuration.

## Database and operations

Schema and **all four applied migrations are unchanged**. Runtime never deploys migrations or creates schema objects. Production startup now rejects superuser/create-role/create-db/bypass-RLS, inherited elevated/owner membership, database/schema CREATE or ownership of public-schema objects through a database-owned inspection method. Real tests demonstrate owner rejection, a restricted non-owner role passing, direct CREATE rejection and rejection after CREATE is granted. This is a conservative startup check, not automatic role provisioning or a full SECURITY DEFINER/function/grant audit. Operator-reviewed migration credentials remain separate; production roles, privilege audit, indexes/lock load, RLS and provisioning still need review.

Before database restore/PITR rollback, stop authentication traffic, rotate session namespace **and** signing authority, invalidate old cache/session records and review durable epochs/families before reopening. Restored PostgreSQL can roll back revocation itself: normal stale-Valkey tests do not certify database disaster recovery. Signing-key rotation with previous keys retains sessions until fences/deadlines; compromised authority requires namespace/all-session invalidation, not indefinite previous-key acceptance. Runtime ACL must constrain the dedicated prefix and connect-redis commands, require real TLS verification, and avoid queue blocking-connection sharing. Capacity/noeviction, retries/reconnect alarms, clock synchronization, orphan reconciliation, retention/purge, outage response, secret-manager delivery and backup/failover exercises are unresolved deployment requirements.

Local init generates an independent signing secret only when creating a new API environment file; existing files are preserved and must receive explicit session fields. No secret value is tracked or printed. Disposable test credentials/roles/TLS material are isolated and cleaned up. Final probes found zero suite-owned databases, roles, cache keys and disposable Valkey containers. Development services started for these checks were stopped with existing volumes retained. The blocked-operation container uses test-only Docker environment/password expansion, with the BE-00F environment/startup-argument exposure; it is **not** a production credential-delivery pattern.
