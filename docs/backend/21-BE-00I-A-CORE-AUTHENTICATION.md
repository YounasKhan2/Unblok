## Decisions and contracts

This slice registers six versioned handlers through a real Nest feature module. Authentication is never `PublicHealth`; the foundation guard recognizes only the six exact server-owned handler references. Other registered handlers still fail closed. No workspace, membership, role, project grant, invite entitlement or business route is enabled.

All responses under `/api/v1/auth/`, including middleware/validation errors, are no-store/no-cache. Existing correlation/error normalization, Helmet, body limits, coarse rate limiting and explicit CORS remain. No ORM row, password/hash, epoch/family/SID evidence or principal is exposed. All bodies use neutral strict Zod contracts and the existing validation pipe/response interceptor.

| Endpoint | Validated input / authority | Success | Failure / exact limits |
|---|---|---|---|
| `GET /api/v1/auth/csrf` | Allowed exact Origin; or the narrow same-origin browser GET rule below | 200 `{csrf}`; explicitly saved anonymous cookie if first use | Missing/null/untrusted origin denied; 429/503 possible; no identity granted |
| `POST /api/v1/auth/signup` | JSON `{name,email,password}` plus cookie-bound CSRF and exact Origin | 202 `{status:"accepted"}` for both new and duplicate canonical emails; stays anonymous unless previously authenticated | 400 invalid body; 403 CSRF; 429 abuse; 503 unavailable/unknown DB result. No automatic login or existing credential overwrite |
| `POST /api/v1/auth/login` | JSON `{email,password}` plus CSRF/exact Origin | 200 `{csrf}` after regenerated SID/CSRF, primary family commit and bounded save | Generic 401 for nonexistent/wrong/disabled or stale credential authority; 400 syntax, 403 CSRF, 429 budget, 503 unavailable/unknown infrastructure result |
| `POST /api/v1/auth/logout` | JSON `{}`, CSRF/exact Origin, fresh live session + primary authority | 200 `{revocation:"confirmed",cleanup:"confirmed"|"unconfirmed"}`; exactly one clearing cookie | No success if primary commit unavailable/unknown. Anonymous/stale retries get 401, not invented idempotent acknowledgement |
| `POST /api/v1/auth/logout-all` | Same, epoch advancement on authenticated current user | Same result; all previous families denied by primary epoch | No cache enumeration or instant cancellation of already-committing requests |
| `GET /api/v1/auth/me` | Fresh request-bound session/principal plus transactional primary revalidation | 200 `{user:{id,name,email,emailVerified:false}}` | 401 absent/expired/revoked/stale identity; 503 dependency failure; no memberships or grants |

Email is a **new local credential namespace**, not an implicit upgrade of User.email contact metadata. Input is trimmed, ASCII-only, case-folded lowercase, syntactically validated and limited to 320 characters. No provider-specific dot/plus folding or contact-email/provider account linking occurs. Identity provider is server-fixed `password`; its subject is a server-generated random UUID. Client-selected IDs/provider/roles/memberships/families are rejected as unknown fields. Name is trimmed and limited to 1–120 UTF-16 units. Passwords are 16–128 well-formed Unicode code points, at most 512 UTF-8 bytes, with NUL rejected; spaces are preserved, no normalization/truncation or composition rule. Existing browser mocks are not wired to these policies.

Signup deliberately requires a separate login. New and duplicate signup return identical status/body without authenticated cookie/user IDs; both perform password hashing and unique-key transactional work. Wrong/nonexistent/disabled login uses the same error code/message/status, apart from request correlation IDs, and an equivalent-cost Argon2id verification (dummy for absent/unusable hashes). **Perfect timing indistinguishability is not proven**: DB contention, hash scheduling and HTTP/network timing remain observable. Rate limits, generic results and bounded work reduce enumeration/guessing; this is not a timing/abuse certification.

Accounts can log in before email verification in this explicitly approved slice. `emailVerified:false` is a contract fact, not a persisted verification workflow. No unverified email can redeem an invitation, link another provider, reset a password or confer workspace rights here. There is no email verification, recovery, OAuth/social login, MFA, password update, frontend wiring, mail delivery or BE-00I-B work.

## Credential persistence and hashing review

Additive migration `20261010040000_password_credentials` creates only `password_credentials`: identity UUID primary/FK with RESTRICT deletion/update, unique canonical email, PHC hash varchar256 and creation timestamp. SQL checks enforce canonical ASCII-style email storage and the approved Argon2id version/parameter prefix. App validation is the full email syntax boundary; SQL does not attempt an RFC mail parser. The table does not alter existing contact email uniqueness or provider identities and does not seed/convert any account. All four applied migration files remain byte-identical. No runtime DDL or migration deployment path is added.

`AccountCredentials` is a narrow privileged database-owned capability, constructed only in the server composition. Two new negative architecture fixtures reject direct and disguised imports by business services. Auth application receives only create/lookup/confirm ports; controllers cannot access raw persistence. Creation hashes outside the existing bounded serializable transaction, then atomically inserts User, opaque Identity and PasswordCredential. A canonical email uniqueness conflict rolls back all new rows and returns accepted without overwrite. At most three complete retries apply only to known P2034 serialization rollback; unknown commit/timeout/network outcomes are not retried as confirmed failure. A failed acknowledgement may leave a committed account; a later duplicate retry is safe but does not reset its password. No distributed exactly-once creation claim.

Bun 1.4.2's native `Bun.password` avoids another dependency and supplies random salts. Explicit Argon2id v19 uses **19,456 KiB (19 MiB), t=2, p=1**, verified from generated PHC output on this host; generated salt and hash fields are each 43 base64 characters (32 bytes). These parameters meet the [OWASP Argon2id minimum](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#argon2id); [Bun password API](https://bun.sh/reference/bun/password) and [hashing guide](https://bun.sh/guides/util/hash-a-password) establish the async API and KiB cost unit. This is a reviewed starting profile, not hardware/load certification. Future parameter upgrades require reviewed SQL/profile compatibility and rehash policy; no weak-profile fallback exists.

Only the exact installed-version PHC profile can reach native verification; malformed/artificially expensive stored profiles perform dummy verification then fail. A random dummy hash is generated at startup. Four in-flight operations per process are admitted with no waiting queue; additional work fails unavailable. A 2s deadline bounds acknowledgement, **not cancellation**. The capacity slot stays occupied until actual native completion even after timeout, so late work cannot admit unbounded replacement jobs. No timed-out result continues to account creation or successful login. Cross-replica aggregate memory/CPU and load remain unverified. Unit evidence covers actual profile, different salts, correct/wrong/dummy/corrupt-profile checks, Unicode boundaries and fifth-operation denial; it does not claim a production hardware benchmark or prove native work cancellable.

## Identity proof, session lifecycle and PostgreSQL ordering

Successful credential verification mints an opaque frozen one-use object held in Authentication's instance-private WeakMap. It is never returned in a DTO. The session resolver consumes that object, rechecks current identity binding/password hash/disabled state/auth epoch in the primary, and returns only server-owned references plus observed epoch. Structural client assertions never resolve. Generic provider IdentityVerifier remains deny-all; no fallback bypass is introduced.

BE-00G family creation has an additive optional observed-epoch input, which real credential authentication always supplies. The existing user lock compares it with the current epoch inside the family-creation transaction. Thus logout-all committed between password confirmation and creation denies the older proof instead of silently upgrading it to the newer epoch. Compatibility callers in prior fence fixtures retain their reviewed server-owned path; this does not permit browser-provided evidence. AuthFences' user→family ordering and unchanged SQL triggers remain authoritative. The HTTP barrier test confirms logout-all commits after proof confirmation but before creation, then login returns 401 with only a clearing cookie and no family minted.

Login reuses BE-00H establishment, SID/CSRF regeneration, strict 30m idle/12h absolute lifetimes, bounded Valkey persistence and terminal finalization/compensation. If replacing a currently authenticated session, a fresh session/principal boundary first confirms and durably revokes that presented family; deleting its SID alone could otherwise be undone by a late SET. Other independent sessions remain active. The real regression restores the predecessor cache payload and gets 401 while the successor gets 200. Stale authenticated cache may deny an initial re-login and clear its cookie; obtain fresh anonymous bootstrap and retry with credentials, rather than reviving stale authority.

`me` uses the owning Tenancy instance's new narrow self-profile projection. Its primary transaction checks registry/context lifetime, user/family locks and authority at entry and completion. It returns no workspace permissions, raw delegate or persistence context. A real HTTP test pauses an already-minted principal before profile access, commits logout concurrently, then observes 401 and rejects that actual escaped principal after request completion. Protected business writes retain their existing transactional fences and denyAll policy; no per-query Valkey reads are introduced.

Logout/outage/finalization contracts remain BE-00H's. Primary commit precedes terminal cookie/cache cleanup; late writes cannot regain authority after confirmed revoke. Cache cleanup timeout returns unconfirmed cleanup, not cancelled DEL. Primary outages and unknown revocation outcomes are 503, not success inferred from cookie clearing. Unknown establishment/family commits or failed compensation remain unconfirmed reconciliation work. Previous reads/responses or commits already ordered ahead of revocation cannot be retracted.

## Browser security and abuse budgets

All POST handlers require JSON, exact configured Origin and constant-time synchronizer token from a valid cookie session, including signup/login before identity establishment. Missing/null Origin, wrong/absent token, simple form bodies and cross-site attempts fail. Cookie signing, HttpOnly/Secure/Lax/Path=/, host-only naming, proxy allowlist and explicit credentialed CORS retain BE-00H settings. Nothing relies only on SameSite.

First-use bootstrap is GET and requires no existing token. Cross-origin clients need an explicitly allowed Origin and reviewed credentialed CORS. Browsers may omit Origin on same-origin GET: only this public bootstrap opts into a corroborated fallback requiring absent (never null) Origin, `Sec-Fetch-Site: same-origin`, fetch mode `cors` or `same-origin`, and request protocol + Host exactly matching a configured allowed origin. Cross-site/none/navigation metadata, missing metadata and unconfigured hosts fail. Mutation missing-Origin policy remains strict with no fallback. Trusted ingress must overwrite forwarding headers, enforce Host/TLS allowlists and block direct API access. Nonbrowser clients can forge Fetch Metadata but cannot thereby read another browser's cookie/token; XSS/same-origin compromise is outside CSRF protection. Header-level loopback tests are **not actual-browser Fetch Metadata, SameSite or deployment certification**.

| Action | IP budget | Account budget | Window |
|---|---:|---:|---|
| Login | 30 | 10 | 15 minutes |
| Signup | 10 | 5 | 1 hour |
| Anonymous/token bootstrap | 30 | None | 15 minutes |
| Logout / logout-all | 30 per action | Authenticated lifecycle and CSRF required | 15 minutes |

Coarse preexisting IP throttle still runs first; endpoint counters are shared atomic Valkey limits under the session namespace's dedicated rate prefix. Account keys use HMAC with the explicit signing secret and are subsequently hashed by the reused limiter; no plaintext email/password key is sent to Valkey or logged. Every attempt counts, including successful and nonexistent accounts; no permanent account lock is introduced. 429 includes Retry-After. Store failure/750ms acknowledgement timeout fails 503; late counter writes may still occur. Secrets/namespaces changing can reset account budgets, and replica deployments must share the same authority/configuration. NAT fairness, distributed attackers, login lockout abuse, signing-key rotation budget reset, production ACL commands, observability and final thresholds need human/operational review. Recovery/invite/email verification budgets are not claimed implemented because those endpoints do not exist.
