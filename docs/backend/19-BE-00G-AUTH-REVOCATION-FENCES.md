## Implemented boundary

`AuthFences` is a narrow database-owned lifecycle capability: create a family after independently verified identity, validate live-session evidence, rotate generation/SID digest, revoke a family, or increment a user's epoch. It exposes no transaction, Prisma delegate, role or permission. Lifecycle methods are privileged server operations; possession of arbitrary user/identity IDs is **not** permission to provision sessions or logout another user. No production caller is bound in this phase. Architecture enforcement rejects direct and disguised lifecycle-capability imports in business handlers; only reviewed infrastructure composition may receive it. Static analysis cannot prove verifier correctness or prevent every function-wrapper capability leak.

`Tenancy.authenticateSession` accepts an opaque assertion through an injected, server-private `SessionVerifier`, then validates its live-session evidence against the primary database. An absent verifier, missing cache result, malformed evidence or mismatched user/identity/family/epoch/generation/SID digest fails closed. The verifier must perform a fresh bounded Valkey lookup and compute the digest of the actual presented SID; session payload references alone must never authorize a caller. There is no installed production verifier, browser DTO, signed internal assertion, cookie middleware or permissive fallback. Test-only verifier symbols and broad policies stay inside the disposable integration suite.

Tenancy still mints frozen, same-instance, WeakMap-owned principals. The private entry now holds identity/epoch and optional immutable session evidence. Every scoped read/write revalidates it in PostgreSQL before workspace/member/resource authorization. Membership, team scope, exact policy grant, OBSERVER restrictions, archival and the dependency gate remain unchanged. Principals cannot be serialized, structurally forged or imported from another instance.

The existing `IdentityVerifier` path captures the current user epoch and rechecks it at scope entry. This preserves independently verified identity use and makes its **already-minted** principals invalid after logout-all. It does not revoke external identity credentials or make a provider assertion session-aware. Future browser authentication must use the session path; routing stale Valkey identity references through `authenticate` would incorrectly bypass family validation and is prohibited. Independently re-verifying real credentials can legitimately establish a new epoch.

## Additive migration

`20261010030000_auth_revocation_fences` adds:

- User `auth_epoch` (positive BIGINT, default 1) and `auth_disabled` (default false). Existing rows retain identity/tenant data. A trigger prevents epoch decrease and increments it when disabling an account, so re-enabling cannot restore old authority.
- `auth_session_families`: UUID family, composite identity/user binding, issuance epoch, positive BIGINT generation, 64-character lowercase SHA-256 SID digest, revocation timestamp, issued/absolute/idle deadlines. No raw SID, credential, session payload or tenant grants are stored.
- Composite identity uniqueness/FK, user/revocation lookup index, deadline/format constraints and immutable family-binding/absolute-lifetime/monotonic-transition trigger. Revocation cannot be undone; digest changes require generation advance. Family IDs are generated by the server and never reused.

Only a trusted identity lifecycle service may create a new family at the current epoch. Rotation validates the existing epoch/generation under locks, cannot refresh stale authority, and cannot extend absolute lifetime or revive an expired family. Family logout is idempotent and revokes rotated descendants. Logout-all increments the epoch; repeated retries may increment it again safely, without an exactly-once claim. Revocation may operate on disabled accounts. No account-management endpoint or identity-provider policy is added.

Revoked records are retained and ordinary DELETE is blocked. Expired records still deny authority. A bounded retention/purge workflow is **not implemented**; it requires separately reviewed retention/recovery rules and cannot reconstruct fences from cache. Runtime credentials must not own tables, disable triggers, truncate fences or have DDL privileges; role provisioning remains pending. Administrators can bypass SQL safeguards.

The original three migrations are unchanged. Fresh deploy, replay and Prisma-visible schema equality pass on disposable databases. The existing pre-correction upgrade test deploys the original two migrations, seeds existing tenant rows using the old column surface, then applies both subsequent migrations; original checksums/timestamps, rows, assignee integrity, default epoch and empty family state are verified. SQL triggers/constraints have separate runtime assertions. Schema diff alone does not certify procedural SQL.

No reset, db-push or destructive down migration is used. The configured development database is not upgraded by this phase's suite; only uniquely named suite-owned databases are created/migrated/dropped. Before rollout, review SQL, backup/restore, Prisma generation/application ordering and migration lock duration. ALTER TABLE/unique-index creation require deployment planning; no large-table or online-migration performance claim is made. Rolling back application code leaves additive columns/tables intact; never remove durable fences to repair a deployment.

## Transactional ordering and exact guarantees

Global order is **user → session family → workspace → resource**. Validation uses user/family `FOR SHARE`; family revocation/rotation use family `FOR UPDATE`; logout-all uses user `FOR UPDATE`. Scoped transactions retain these locks through commit. Existing serializable isolation, 2s acquisition/5s callback bounds, 1.5s lock timeout and 4s statement timeout are preserved. Family rotation acquires its exclusive lock before validation, avoiding lock upgrade. No Valkey/network I/O belongs inside a database transaction or policy callback.

An earlier protected write holding valid fences commits before a successfully acknowledged conflicting revocation. If revocation wins, a stale write cannot commit: it observes a mismatch or PostgreSQL aborts the stale serializable snapshot. Tests observe `pg_blocking_pids` before releasing barriers, and verify committed business state. SQLSTATE 40001/40P01 from raw queries maps to the existing conflict error; no side effects are automatically retried. Retry only a complete idempotent operation, revalidating authority each time. [PostgreSQL 17 row locks](https://www.postgresql.org/docs/17/explicit-locking.html) and [serializable isolation](https://www.postgresql.org/docs/17/transaction-iso.html) explain the tested conflict behavior.

Both family logout and logout-all are tested in both lock-acquisition orders. A long-running earlier transaction can exhaust the unchanged revocation lock wait; that result is unavailable/unconfirmed, not successful revocation. A bounded caller retry must obtain a confirmed commit before acknowledging success.

Session deadlines use primary `statement_timestamp()`, not a cache timestamp or transaction-start clock. Authority is checked at transaction entry and after the scoped callback, so expiry during work rolls back mutations. This is not an exact physical commit-time expiration guarantee: the final check and commit have a small interval. Revocation ordering is the stronger lock/commit guarantee. Previously produced reads/responses and external work are not instantaneously canceled.

After confirmed PostgreSQL revocation commit, restoring a stale Valkey record cannot restore authority, including for an already-minted principal. A real Valkey delayed SET test destroys/restores the payload after revocation, confirms it exists again, and verifies both fresh authentication and protected writes reject it. There is no positive fence cache, read replica or stale-on-error fallback. This suite proves the database barrier, **not** the still-unimplemented session wrapper's callback cancellation.

PostgreSQL outages yield generic `AuthUnavailableError`; no protected callback executes. Invalid/revoked evidence yields `AuthDeniedError` at the lifecycle boundary / generic `TenantAccessError` at Tenancy. Future transport must map unavailable dependencies to 503 separately from inaccessible authority; no existing API error contract is changed. Unknown commit outcome is unconfirmed revocation, never success inferred from cache deletion. PostgreSQL backup rollback can roll back epochs too: a separately reviewed recovery runbook must invalidate old session namespace/signing authority/cache before reopening authentication. No disaster-recovery certification is claimed.
